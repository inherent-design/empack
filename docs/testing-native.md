# Native and consumer regression coverage

Use the commands in [Verification](testing.md) to select checks. This reference describes what the native fixtures and consumer probes establish and where actual application acceptance is still required. The [registry](../tests/verification/README.md) owns test identities and required variants.

## Terminal and native process checks

The optional [Java/bootstrap/native console probe](../bootstrap/tests/test_native_runtime.py) accepts a prepared disposable instance; use its `--help` for explicit paths. It expects normal input to return 0 and terminal interruption or stopped-runtime cancellation to return 130, with terminal restoration and no surviving owned process. It supplements the fixed suites and consumer procedures.

On macOS and Linux, the normal native suite includes a real controlling-PTY test:

```sh
cargo test -p empack-lib --lib inherited_runtime_owns_terminal_and_restores_it -- --nocapture
```

It supervises an isolated runtime process, checks foreground ownership before any console reads, sends input and terminal Ctrl-C, and verifies normal shutdown, cancellation, nonzero exit, failed exec, disabled terminal suspend keys, external stop/resume, cancellation while stopped, and restoration of terminal ownership and settings. The fixture changes terminal settings to make restoration observable. It proves host process/terminal behavior; it is not Minecraft gameplay acceptance. The Unix executable test `cli_pty_instance_launch_restores_console_after_input_interrupt_and_failure` connects public export/install to the selected product's `instance launch` through a controlling PTY. A fixture runtime reads console input and changes echo settings; normal shutdown, graceful terminal Ctrl-C, nonzero exit and host cancellation must restore the invoking shell's settings and allow a follow-up read. The test checks the final diagnostic/status, retirement of the owned group, preserved player bytes and a subsequent public launch. It uses the compiler-bound native test runtime with an explicit signal handler, not Java or generated server entry points; those and Windows console behavior require separate evidence.

Unix confirmation, text, selection and fuzzy selection share a cancellation-aware byte reader and captured terminal-mode owner. Text and selection fixtures use real PTYs to check Unicode editing, defaults, original option indices, paging, optional Escape, token cancellation without input, and Ctrl-C during partial UTF-8 or escape sequences. They compare restored flags, control characters and speeds and check cursor visibility. The `native_unix_prompt_adapters_retire_input_and_host_interrupts_before_followup` case exercises `LiveInteractiveProvider` through a controlling PTY, interrupts each adapter through both keyboard input and a host signal, then obtains a fresh rejection on the same thread. These native adapter checks complement the public CLI approval journeys; they do not establish Java, launcher or GUI acceptance. Run them through the verification runner on the required native hosts and product feature sets.

The Windows ConPTY case connects public export/install/launch to the executable's Ctrl-C diagnostic, status 130 and confirmed child retirement. Its compiler-bound private runtime registers a [console control handler](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler) before announcing readiness and stays alive through Ctrl-C, so cancellation cannot race a completed child. The fixture owner verifies kernel creation time before retaining cleanup authority through a process handle. A follow-up launch must succeed, and game/player bytes and attributes remain unchanged. ConPTY merges stdout/stderr, so this does not prove separate stream routing, actual Java behavior or Unix terminal restoration. The ignored private runtime's ordinary invocation is not acceptance evidence; the product has no corresponding test control.

The Unix [output-stream fixtures](../crates/empack-tests/tests/support/streams.rs) run the actual CLI with a controlling PTY and independently redirected results or diagnostics. They check automatic and explicit color policy, prompt eligibility, preserved files after refusal, and final terminal contents at 12, 40 and 80 columns. A controlled slow version response exercises progress clearing, quiet and JSON output, host interruption, cursor restoration and a later successful operation. Verbose logging must retain its messages without creating a second progress region. The controlled response establishes display and process behavior, not actual JVM compatibility. Shared display tests cover coalesced observations and phase changes separately from these public-command checks.

Finite-command screen checks use the [shared terminal capture helper](../crates/empack-tests/src/harness/terminal.rs). Windows capture drains output concurrently with ConPTY teardown after child exit, retaining the 15-second and 1 MiB limits; a temporarily empty pipe is not EOF. The update fixture checks the complete screen at 40 and 80 columns and verifies that project files remain unchanged.

Managed Prism tests separately verify the root icon's seed policy and rejection of an explicit managed policy before publication, while keeping other PNGs managed. Engine launch fault injection separately establishes that failed terminal cleanup after confirmed retirement reports the error without retaining runtime ownership; uncertain-retirement tests still require recovery. Signed-channel tests use the native release producer and a persisted Prism layout, reject managed icon updates, and preserve launcher bytes through corrected seed updates and launch preparation. Historical managed-icon fixtures verify migration to seed without conflict overrides.

The Windows termination-denial fixture keeps a real owned job alive while checking that failed termination cannot establish retirement. Dropping the owner explicitly retries job termination before closing its kill-on-close handle; the fixture must then reap the child within the existing bound. This cleanup attempt does not change the already reported uncertainty into a retirement proof or clear recovery state.

The Windows captured-runtime fixture first observes EOF on both output pipes while its private child remains alive in the owned job. Separate calls through the production capture supervisor then exercise deadline expiry and cancellation after observed startup and closure of the child's output handles. Retained process handles are checked against kernel creation times before interruption and must be signalled after retirement. These native checks complement the exact-output, overflow and disconnected-progress cases; they do not establish Java or GUI acceptance.

Executable finalization is tested separately from process supervision:

```sh
cargo test -p empack --bin empack
cargo test -p empack-lib --lib launch_failure_summary
```

These checks retain cleanup, recovery, uncertainty and partial-effect diagnostics when cancellation is set, retain success after a late interrupt, and verify that launch failure headlines do not imply that the runtime never ran. The executable fixtures test result presentation; the engine and PTY fixtures establish ownership cleanup and actual process retirement.

The `managed_runtime_exit_uses_empack_classification` host test runs fixture children with exit statuses 0, 7 and 130, then verifies managed CLI classification and the retained runtime status. A Unix companion checks actual SIGINT versus SIGTERM; the Windows status test checks console interruption versus an access violation. These checks do not launch Java. The generated-server-script test carries a fixture runtime exit 130 through the unchanged script, real bootstrap JAR and selected native engine; the controlling-PTY executable test also covers a runtime returning 130 after terminal Ctrl-C. Cleanup and recovery failures remain separate negative cases. The Unix `cli_interrupt_exits_130` test sends SIGINT to the actual empack executable during a bounded local HTTP request and checks both exit 130 and stderr. Run it against a freshly built binary to test executable wiring:

```sh
cargo build -p empack --all-features
cargo test -p empack-tests --all-features --test cli_exit_codes cli_interrupt_exits_130
```

Resource-lifetime checks distinguish cancellation from worker retirement. The runtime's dropped-handle test writes and synchronizes a real four-byte file, then holds its owner behind a channel. Dropping the caller must cancel the worker token without releasing reservations, evicting the active operation or publishing a terminal result. Releasing the owner permits a typed cancelled result and zero remaining reservations. The bounded registry still requires explicit result release before admitting another operation. Readiness, retirement and release use channels and observed phases rather than elapsed sleeps as evidence.

The CLI-host build cancellation case retains one preparation while an approved bundled build acquires an incomplete response from an owned loopback server. Only the server's request notification triggers host cancellation. The host must return its typed interrupted result, retire the response socket and release that operation's reservations while preserving the other preparation's complete reservation. Author, prior-artifact, world and host-neighbor bytes, readonly flags and an explicit empty directory remain unchanged; releasing the other preparation permits new work. This controlled host case does not execute the CLI binary or establish external-provider, terminal or consumer behavior.

Artifact-cleanup confinement uses the same public Engine test for Unix directory symlinks and Windows directory junctions, both at `dist` and beneath it. The Windows fixture verifies the native reparse attribute before requesting cleanup; refusal must preserve the outside sentinel, junction target and neighboring artifact without creating recovery state or retaining reservations. The fixture removes its own junction afterward. This does not exercise file symlinks or claim that the Windows variant ran on another host.

The executable multi-output build journey explicitly uses `--cpu-jobs 1` for sync, preview, both archive outputs, late-template refusal, repaired rebuild and cleanup. It compares complete mrpack and subscribed-Prism inventories and preserves prior artifacts on failure. This checks the public worker limit across batch stages; it does not measure an OS memory quota or prove admission across separate empack processes.

A controlled-clock unit case checks the shared transfer budget without network or filesystem activity. Elapsed time and consumed bytes carry into later requests; narrower limits and failed charges cannot reset that allowance. Exact expiry also rejects zero-byte work. Tokio clock controls are a library development dependency; they are not a product configuration or a substitute for actual I/O retirement.

Captured Unix processes have a separate tiny-limit check: each stream may use its full allowance, while overflow with an already-full progress queue must report the limit failure after the owned group is gone. Existing tests retain closed-pipe deadlines, descendant retirement and disconnected progress observers. These checks have a Windows job counterpart using literal `cmd.exe` scripts: exact per-stream limits, overflow behind a full progress queue and complete output after the observer disconnects. Overflow must return its specific limit error through confirmed retirement, rather than timing out or losing job ownership.

These cases cover captured-process supervision. UX-080 separately binds atomic worker, estimated-memory, scratch-byte and open-file admission; bounded registry and retained-output ownership; shared Engine preparations; CLI-host capacity refusal/retry and running-acquisition cancellation; and the executable's single-worker build batch. Each binding requires execution on its declared host and product variant; a complete case definition is not a passing run or final-artifact qualification.

A macOS zombie fixture holds an exited child unreaped, observes the real group-signal failure, then reaps it and confirms absence. A signal error cannot override subsequent proof of retirement. A separate real live group with an injected signal-denial result must still fail retirement and retain the recovery diagnostic.

Chunked metadata and payload HTTP fixtures require the typed byte-limit or deadline error for each stalled-response case, together with socket retirement; an unrelated transport failure cannot satisfy the byte-limit assertion. Payload acquisition checks also retain reservations through the last reader, fit two seven-byte inputs into a sixteen-byte scratch allowance, and retire stalled verifier/response ownership when the caller cancels or drops its future. These reuse existing component tests. Reservations are admission estimates, not measured OS memory use or enforced filesystem quotas. Inherited interactive consoles do not have captured-output limits.

The executable's local proxy fixture explicitly selects blocking reads after accepting a connection, then applies its bounded read timeout. It cannot rely on platform-specific inheritance of the listener's nonblocking mode. Proxy-thread panics retain their original cause. Native image cleanup reports the freshly observed owned backing's entities and exact-file open handles when its expected mount is already absent. It never selects the host filesystem in that state or grants new detach authority. The busy-reader case also records a descriptor-only observation for its own process after dropping the file, alongside the original device and inode; descriptor reuse or diagnostic failure is not retirement evidence. A busy-detach failure remains a failure; these diagnostics do not establish its cause or extend cleanup limits.

## Display and argument boundaries

Human display regressions distinguish external text from empack-owned terminal styling. Captured help text uses the same renderer: inherited path values preserve ordinary Unicode while directional controls appear as visible escapes. Status, table and progress data escape terminal/directional controls; complete diagnostics preserve intentional line layout, while cells and progress labels stay on one line. Narrow Unicode table fixtures must not panic at a multibyte boundary. Executable finalization and bootstrap error tests retain the error outcome while rendering control characters visibly. JSON values and inherited game/tool streams have separate contracts and are not rewritten by this presentation policy. Verification Markdown/HTML cells retain their own HTML-escaping regressions.

Generated-server JVM fixtures place host scratch outside the instance, so JVM performance files cannot contaminate author-preservation assertions. Windows fixture paths entering external JVM argv stay within the documented ANSI encoding scope; direct native launch tests retain Unicode Java paths, and packaged-JAR file tests separately cover relocated Unicode distributions and static arguments. These boundaries do not establish lossless arbitrary external JVM arguments; see the [encoding appendix](troubleshooting.md#bootstrap-encoding-appendix).

## Managed consumer interpretation

Managed Prism configuration tests include absent, unsupported, duplicated and misplaced version markers, command shadowing, multiline quoting, and hash-prefixed settings with open quotes or trailing continuations under both supported versions. Include ordinary space/tab controls and Unicode whitespace at key, section, comment and value boundaries. Accept LF/CRLF and unterminated final lines; reject bare CR and unsupported controls. Unicode display-value fixtures remain accepted without changing author bytes. Semicolon controls preserve the effective lifecycle settings. Compare the same fixtures with Prism 11.1.1's actual `INIFile::loadFile` implementation, using a clean upstream checkout and Qt 6.4 or newer within major version 6, as required by that Prism revision. Qt is opt-in test tooling, not an empack runtime dependency. The probe rejects unsupported Qt versions before compilation. Unsupported Qt builds provide supplemental diagnostics, not qualification of Prism 11.1.1. Consumer-parser execution is separate from launching Minecraft. Its receipt records application and empack revisions, dirty state, fixture SHA-256, platform/architecture, compile/runtime Qt versions, compiler identity, build configuration, probe executable digest, observation time and source-input digests. The schema-2 record retains every fixture observation; settings failures return a nonzero status after writing the observations. The gate recomputes the outcome from those settings rather than trusting the status field. Dirty-source results remain diagnostic only. The producer currently runs on Linux and macOS; the required parser case selects Linux, matching the CI runner. The same observations support UX-053's Prism integration and UX-083's headless configuration contract without multiplying execution counts. Actual import and startup remain UX-084 obligations. This does not qualify other consumer operations or hosts. Actual consumer and fresh-user observations use the separate [operator acceptance records](verification-acceptance.md), bound to the candidate products and retained supporting files. Their reader tests do not perform those tasks. The public CLI build case selects ten named fixtures from that same corpus across three managed recipe variants. It validates the generated baseline against literal content before checking exact custom configuration bytes and unchanged remaining members. Rejection preserves author files, attributes and prior archives. A separate standalone bundled control retains author-owned settings without managed hooks. This executable boundary supplements the complete validator corpus, representative engine preparation and the independent consumer probe; it does not run Prism, exercise server templates or qualify a final archive.

The same managed-integration group separately binds server batch preparation and generated-script execution. Changed custom entrypoints are refused for reference snapshots and subscribed recipes; byte-identical copies receive the required output attributes in ZIP, TAR.GZ and 7z without changing source permissions. Standalone bundled scripts retain their separate customization policy. The executable fixture runs unmodified generated scripts through the selected product and fixture Java, checking preparation ordering, refusal and status handling. It does not establish a complete server export or JVM startup. Native results without the supported Prism parser cannot complete this group; actual consumer import/startup remains the separate, mandatory UX-084 gate.

The probe compiles upstream `INIFile.cpp` and `Json.cpp` without vendoring or changing their parsing code:

```sh
python3 scripts/check-prism-config.py --prism-source /path/to/PrismLauncher-11.1.1 --qmake /path/to/qmake > /path/to/prism.json
```

Use a clean checkout at `7d2d3c1ec6fcf8255ebacd02d9f792688575dfb4` and supported Qt 6 development tools plus `make`. The shared fixtures also run through empack's public build preparation. The probe verifies accepted settings and reproduces the legacy shadow and hash-prefixed quote/continuation counterexamples; it does not certify every rejected representation.

Shared scalar fixtures cover leading variant markers, separators, whitespace, quotes, backslashes, Unicode, adjacent hexadecimal escapes, encoded controls/NUL and empty values under both supported INI formats. Rust checks its encoder output against the fixture bytes; the probe reads `name` back as a `QString` equal to the original value. Records bind the encoder source alongside consumer, fixture and build inputs. Changed scalar content or type fails admission. Java-properties interpretation is checked separately by the `server-cli` live fixture below.

The existing `server-cli` live fixture checks generated server properties across reference/bundled ZIP, TAR.GZ and 7z exports, then reads the actual archived bytes with the JDK’s `Properties.load(InputStream)` and `Properties.load(Reader)`. It compares code points with the original metadata, verifies empty values and key counts, and includes a changed-scalar control. Missing values, explicit non-UTF-8 templates and duplicate destinations are rejected for both server deliveries in every format, preserving author snapshots and all previous archives. The probe uses the fixture’s restricted environment with `LANG=C.UTF-8` and `LC_ALL=C.UTF-8` on Linux so Java can read its Unicode source and input paths; product commands retain their controlled C locale. It records Java’s runtime version and native filename encodings and has a bounded invocation; it does not launch Minecraft. The `server-cli` JUnit report retains the environment line even when the test passes. The source-mode properties probe requires a full Java 21 JDK with the compiler module. Missing or unexecuted consumer evidence remains nonpassing.

Managed server tests check archive attributes in ZIP, TAR.GZ and 7z for identical scripts captured with and without executable source permissions. On Unix, extract and directly execute the shell entry points with controlled fake external tools. Windows tests execute batch entry points with `EMPACK_NO_PAUSE=1`, checking full diagnostic text, empty syntax-error output and preserved exit status. Source permissions and authored bytes remain unchanged after candidate preparation.
