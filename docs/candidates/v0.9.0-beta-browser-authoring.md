# v0.9.0-beta candidate: portable authoring

This candidate defines an editable modpack project shared by native and browser
hosts. It is a proposed contract, separate from the implemented v0.8 design.
Type and crate names below describe boundaries, not existing callable APIs.

## Project workflow

The editor accepts dropped files, selected files, imported archives and existing
projects. It inspects inputs, proposes changes and retains an editable draft.
Saving a draft does not require complete resolution or all content to be available.
Executing an export requires a validated, revision-bound plan and verified inputs.

```text
Input assets → inspection → proposed changes → editable project
                                                  ↓
                                      resolution and decisions
                                                  ↓
                                verified export plan → output
```

| Action | Result |
| --- | --- |
| Save project | Author documents, custom sources and state needed to reopen the draft |
| Export distribution | Verified output for the selected consumer |
| Apply to directory or instance | Native installation with ownership and recovery checks |

An exported distribution is not necessarily a lossless author-project backup.
The project-save format must preserve templates, profiles, bindings and custom
sources, including unresolved requests. Its wire format remains a design decision.

## Crate boundaries

```text
empack-core: identities, invariants and pure planners
    ↑
empack-engine: editing, resolution, import/export and verification
    ↑                                      ↑
empack-native                          empack-wasm
    ↑                                      ↑
empack-cli / empack-app                 browser SPA
```

`empack-core` remains independent of native I/O and browser APIs. The portable
engine owns semantic behavior; hosts supply capabilities. `empack-cli` can replace
the executable crate name while keeping the installed command `empack`.
`empack-app` can use a native Rust backend through Tauri and share its web UI with
the SPA. Desktop execution need not pass through WASM.

The existing engine requires extraction: native paths, staging, content leases,
Tokio execution and installer processes cannot become browser requirements.
Filesystem publication and process containment remain native responsibilities.

## Editable state and assets

A `ProjectDraft` contains authoring documents, requests, bindings, output profiles,
a virtual source tree and asset references. An `Asset` has an opaque handle, byte
length, observed content identity, original integrity evidence and availability.
An observed digest does not become independent source authentication.

The virtual source tree maps portable project paths to immutable asset references.
Edits create new content and replace mappings. Undo and redo retain prior mappings
and their asset leases. Large JARs and archives stay in host storage; bounded reads
avoid copying the whole pack into WASM memory or each undo snapshot.

Drafts may be incomplete. Validation produces diagnostics and outstanding decisions;
only valid drafts become executable plans. Background results carry their source
revision. Results from an older revision cannot silently overwrite newer edits.
Export plans retain their own immutable inputs while the editor remains usable.

## Host capabilities

| Capability | Contract |
| --- | --- |
| Content access | Bounded streams or random-access reads from opaque handles |
| Content retention | Store verified bytes; keep referenced assets alive |
| Network transport | Bounded requests with explicit permissions and cancellation |
| Project persistence | Save and load revisions without exposing OS paths |
| Export destination | Bounded writes, backpressure, finalization and failure reporting |
| Runtime preparation | Optional installer/process capability with verified results |

Archive interpretation, recipes, hashing and verification remain shared where
portable. Hosts do not implement competing interpretations of valid distributions.
ZIP, tar and 7z implementations need target-specific compilation and behavioral
checks; their presence in the native build does not establish WASM support.

The initial browser runtime uses one dedicated worker. Long operations yield and
check cancellation. Native `Send + Sync` and blocking-task requirements do not
constrain browser handles. Cancellation, task retirement and retained content
ownership remain distinct. Worker loss cannot imply successful save or export.

## Browser storage and export

IndexedDB remains an active standard. Workers provide execution isolation, not
storage. OPFS is the proposed large-file backing store; IndexedDB can hold small
project records. Synchronous OPFS access is confined to dedicated workers.

Custom imported files default to retained workspace copies. Optional external
references distinguish available, permission-needed and missing content. Custom
sources are project data, not disposable cache. Cleanup preserves references from
saved drafts, undo history, active plans and pending operations.

When metadata and content use different stores, save bytes first, then commit a
revision referencing those bytes. Interrupted saves may leave reclaimable unused
content; they must not claim a durable project whose assets were never retained.
Multi-tab ownership and revision conflicts require explicit coordination.

Browser quotas, eviction and private-mode behavior are host constraints. Request
persistent storage where available, report quota failures and provide portable
project backups. Browser-local autosave is not equivalent to an external backup.

Export uses a writable file destination where supported, with a staged-download
fallback. Limits and finalization behavior must be visible before large exports.
A partially written or unverified artifact cannot be reported as complete.

## Capability coverage

| Feature | Browser behavior |
| --- | --- |
| Editing, bindings, inspection, resolution | Shared engine with browser transport |
| Archive import and distribution export | Shared codecs over virtual content |
| Restricted downloads | User-selected files verified against exact obligations |
| Templates and configuration | Virtual source tree and shared rendering |
| Signed release preparation | Requires an explicit key custody and signing design |
| Java probes, loader installers, game launch | Requires a native host or companion |
| Native instance repair and recovery | Retains native publication safeguards |

A missing capability is reported before execution. A browser can prepare a server
plan without executing Java installer processors. Installer-on-recipient delivery
is a distinct recipe, never a silently substituted fully prepared runtime.

Provider and download URLs must be checked for browser CORS support. WASM and
workers do not bypass CORS; opaque responses cannot supply verifiable bytes.
Unavailable routes require manual input, a native companion or a separately
specified service. A public SPA cannot conceal a shared provider API secret.

Restricted-download continuation displays the exact requirement and download page,
accepts a selected or dropped file, verifies original assertions, retains the asset
and re-prepares the plan. Importing into local browser storage need not upload the
file to a remote service. Filename matching alone never authorizes association.

## Acceptance contracts

The first portable scenario is local JAR and configuration import, metadata and
placement editing, preview, project save/reopen and Prism snapshot export. Native
and browser hosts must produce equivalent semantic inventories from the same
inputs. This establishes the boundary before expanding provider and consumer work.

Tests cover stale asynchronous results, undo asset retention, missing custom files,
quota failure, interrupted saves, cancellation, wrong restricted downloads and
partial export rejection. Browser acceptance must exercise actual browser storage
and downloads; a native in-memory adapter alone does not establish browser support.
Existing world protection, provider identities, file roles, evidence policies and
consumer inventories remain obligations across hosts.
