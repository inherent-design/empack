# Dependency assessment and runtime migration

`update` previews dependency changes by default, without changing author documents, installed content or persistent operation state. `--apply` permits a separately prepared and approved application. `migrate` resolves a proposed Minecraft and loader request before editing the author project. Both require a coherent current lock.

## Prepared update reports

`update --json` returns a schema-1 preview. `requested` lists the selected logical dependencies once, including multi-file sources. `source_kinds` identifies provider, local and URL sources; local inputs are not reported as provider catalog observations. `discovery` contains provider observations when catalog work was applicable; it is null for an entirely local update. `discovery.scope` retains the selected catalog keys and retained-inventory count; `complete` and `summary` describe only those observations, and `blocking_dependencies` names missing evidence. Catalog completeness is separate from `proposal`, which is `ready`, `unchanged`, `blocked`, `incomplete`, or `partially-ready`. Readiness comes from native preparation of the combined candidate, including retained relationships and file placement, rather than a catalog count. A proven unsatisfied exact requirement blocks the requested selection; missing evidence alone makes it incomplete. It does not prove game behavior.

`selected`, `changed_selections`, and `author_pin_changes` distinguish checked selections, changed exact pins or manual content assertions, and deliberate author policy edits. Refreshing a local source can change its accepted evidence in the lock without changing the payload bytes. `file_changes` records planned paths, content hashes, lengths, and permissions before and after each change. `references` counts slots retained as references; `blocked_groups` and a typed `diagnostic` explain unavailable preparation. Blocked, incomplete, and partially ready previews are unsuccessful even when useful discoveries or independent groups remain available. JSON is preview-only; application uses a fresh, separately approved preparation. The report is not an execution grant or a serialized plan protocol.

## Update evidence

`ProviderCatalog::analyze_provider_update` uses the same bounded scan for update preparation and retains its exact provider closure. Normalization reuses that evidence and the existing file-role/participation rules without another catalog scan or a fresh transfer allowance. A normalized provider group is not a complete pack candidate or a native execution grant: combined preparation still checks retained dependents, placements, file conflicts and captured inputs. If discovery or preparation fails, useful independent findings remain available alongside the original typed cause. An exact selection requested for analysis does not itself edit an author pin.

`ProviderCatalog::assess_updates` supplies internal catalog observations to the update analysis; the CLI serializes them under `discovery` in its schema-1 preview. Each selected dependency has its logical key, human title, canonical provider/project identity and exact current selection. Catalog observations retain human version labels when the provider supplies them.

| Field              | Meaning                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------- |
| `current`          | Exact locked selection                                                                      |
| `permitted`        | Selection allowed by author pin and requested release policy                                |
| `compatible`       | Best available selection matching the requested game/loader, without the release preference |
| `upstream`         | Most recently published available selection in the observed project catalog                 |
| `catalog_complete` | The bounded available catalog was read completely                                           |
| `reasons`          | Stable codes for pins, policy, incompatibility or unavailable evidence                      |
| `diagnostic`       | Keyed failure context without credentials or download locations                             |

The report records whether all author roots or exact selected keys were assessed, lists those roots, and counts locked selections retained as context. `update KEY…` limits catalog work to those explicit keys; it does not merely hide other rows. Unknown or repeated keys fail locally before catalog access. Required dependencies can still be queried to validate the selected closure. Retained selections remain compatibility context, not independently scanned roots. A complete selected assessment is not a complete whole-project assessment.

`summary` derives disjoint counts from the same row facts used by text output: change available, held, unknown, manual, unavailable and conflicted. Held includes exact pins and unchanged selections; observation labels do not change exact identity. Catalog completeness is scoped to the selected dependencies and required relationships. It does not determine native proposal readiness by itself. The default text view leads with the proposal outcome, followed by the checked dependency count and aligned version-check counts. It shows changes and problems; targeted checks also show kept and manual dependencies so the selected question is answered. Larger default reports summarize those repetitive rows. `--details` includes every row, exact candidate identities and check information, with the observation time after the results. Successful completeness flags and internal evidence labels are not default output. JSON retains the observations for the selected scope alongside the native proposal. Joint validation and incompatibility declarations remain separate from per-row counts.

`release_policy_source` identifies the operation override, per-dependency preference or project default. `compatible_matches_release_policy` compares the Minecraft/loader-compatible observation with the automatic catalog policy choice, before applying an author's exact pin; null means no comparison was established. Detailed human output labels this observation “Minecraft/loader match”; it does not establish compatibility with other installed mods.

Compatible ranking prefers the primary Minecraft version, then explicitly accepted alternatives in order, then publication time. `prefer-stable` ranks stable releases before prereleases; `stable-only` excludes prereleases; `any` has no stability preference. These policies govern provider versions, not publisher subscription channels. A different permitted selection need not be newer than the current pin. An exact pin remains the permitted selection even when upstream has newer files.

`catalog_validation: runtime-compatible-payloads` makes the admission boundary explicit. Every catalog record must have consistent canonical identity, ownership, availability, publication and runtime metadata; duplicate or conflicting identities still invalidate the scan. Payload file names, roles, locators, digests and dependency declarations are normalized for runtime-compatible candidates. An unrelated historical payload cannot invalidate a current candidate merely because its files cannot be installed by this host. The same payload is fully checked when explicitly selected or when its runtime becomes eligible. `upstream` is a catalog-metadata observation, not a verified downloadable distribution. Unavailable records remain metadata observations without payload admission.

Provider decoding retains a typed field and invariant in `provider_problem` when available, plus canonical project/selection context in `diagnostic`. Structural JSON paths are restricted to known field names and numeric indices; dynamic map keys and raw error values are redacted. Empty collections, duplicate names, unsupported native placement, invalid locators and invalid digests keep their catalog failure classification. Internal model errors are not relabeled to make an assessment continue.

The scan shares a transfer allowance and deadline across roots and the joint closure check. Exceeding a catalog bound fails the scan; a partial page set cannot be reported as the newest selection. Authentication, throttling, malformed records and unavailable providers remain unknown evidence. Root-local invalid records, identity mismatches and unsupported content leave that row unknown while later roots retain the same cumulative transfer allowance and absolute deadline. Provider parsers classify malformed external records at their input boundary, including a listed Modrinth version with an empty file list. Internal model errors are not globally reclassified as provider evidence failures. Authentication, throttling, exhausted bounds and transport failures stop subsequent queries. No failure resets the allowance. Joint validation requires all necessary root evidence. When root evidence prevents the check, `joint.blocking_roots` names those rows and `joint.reasons` includes `incomplete-root-assessment`. `update` emits useful partial findings before failing when required evidence or native preparation is incomplete; no extra strict-mode switch is needed. Manual sources have no implicit provider update. Reports contain an observation time and no credentials or download locators.

Catalog progress reports actual root/page observations and the required-closure phase. The CLI renders it on stderr, keeps only the latest pending observation, and limits updates to two per second. Interactive terminals use a spinner without a percentage or ETA; redirected output uses plain messages. `--quiet` suppresses provisional progress while retaining stdout reports and failure diagnostics. Progress cannot replace the terminal outcome or reset cancellation, transfer allowance or deadline.

Per-root candidates and joint validation are separate. The joint check uses the required-dependency closure, including exact root pins. `joint.state: validated` means the required relationships are complete and consistent. It does not establish that the full retained inventory can be installed together.

The catalog report lists `joint.declared_incompatibilities` between the proposed closure and retained exact selections, including retained reverse assertions. These are provider declarations, not placement-aware conflict decisions. Disjoint client/server content may satisfy them. `joint.declarations_complete` is false when the scan did not run or reached its output limit or shared deadline. Reaching a bound preserves completed rows and the partial list with a `catalog-limit` or `deadline` reason. The scan uses the original catalog deadline, including while comparing retained selections. Missing assertions do not prove compatibility. Update preparation composes the complete candidate and checks actual file participation before publication.

Catalog discovery does not verify new file-role bindings or native destinations. Native update preparation checks those before reporting a ready proposal. Neither establishes runtime startup or gameplay. `blocked` does not prove that no alternative combination exists; this resolver does not perform an unbounded search over version combinations.

## Runtime candidates

`migrate --minecraft VERSION --loader FAMILY --plan` composes candidate intent in memory. Loader versions can be explicit; otherwise a valid locked runtime remains selected or the runtime catalog supplies a compatible version. New runtime requests are checked against official game/loader catalogs. `--accept-version` supplies the complete alternative-game list for the candidate; omitting it clears that list.

`--replace KEY=PROVIDER:PROJECT_ID` explicitly replaces an existing provider root. Its logical key, content kind, environment and integration bindings remain. The replacement uses compatible version policy rather than carrying an exact pin from the old provider project. Unknown keys, duplicate mappings and non-provider roots are rejected. Empack does not infer replacements across loader ecosystems.

Still-compatible provider pins and original content assertions remain unchanged. Unsatisfied roots use the normal provider/file resolution and closure checks. Implicit required libraries are revalidated against the candidate runtime. A compatible locked selection stays exact; an incompatible selection is resolved again under the shared catalog budget. A new exact requirement from a selected root is honored without promoting the library into author intent. Existing logical keys remain stable. Explicit root pins still require deliberate policy changes. After resolution, sync and migration also check retained provider entries outside the new closure: these entries still ship through their locked placements. One bounded exact-selection batch shares its transfer allowance and deadline across all remaining entries. An incompatible retained entry blocks the operation with its logical key and instructions to remove or replace it deliberately. Unavailable or invalid provider evidence also blocks preparation; it is not compatibility proof. No migration deletes unused libraries automatically.

An ambiguous file set or incompatible exact pin stops preparation with a diagnostic; edit the binding or version policy deliberately before retrying. Local content is retained, but its runtime compatibility remains the author's responsibility.

The schema-2 plan report compares the union of current and proposed lock keys, including explicit roots and transitive entries. JSON and text include both exact selections, file roles, destinations, layers, side requirements and one shortest known root-to-dependency reason chain. It separates retained/changed/added/removed entries from required/newly-required/no-longer-required retained status, and marks explicit replacements and manual compatibility verification. Missing edges prove that an entry is no longer required only when reachable dependency coverage is complete; otherwise the report marks its requirement status unknown. Before and after runtime selections include the accepted alternative game versions. `--plan` never saves pending work or changes the project. It is a semantic candidate report, not an authorization token or proof that native replacement will succeed.

## Publication and continuation

```text
captured author + bindings + lock
    -> proposed runtime and explicit replacement identities
    -> compatible selections and dependency evidence
    -> coherent candidate intent and lock
    -> native capture and exact replacement preview
    -> approval -> verified publication
```

Each file's before/after evidence includes its logical role, expected size and digests, accepted content observation, acquisition source, and provenance. The report uses the lock's wire representation for these fields, so a changed source or byte assertion remains visible even when the provider pin and destination stay the same.

`SyncRequest::Migration` carries a fresh `ProjectRevision`, resolved candidate and verified acquired content. Its constructor grants no write authority. Preparation rejects unrelated authoring changes, invalid retained selections and stale raw input documents. Publication uses the same native file verifier, exact grant and recoverable multi-document journal as other author mutations.

With `--materialize`, unavailable exact bytes can suspend the operation. Pending synchronization schema 2 retains its migration mode, candidate and original document binding. `pending resume ID --file KEY=PATH` rechecks that binding and the supplied bytes, then requests new approval. The saved candidate does not authorize overwriting a subsequent author edit.

Migration does not port configurations, worlds or private JARs. Java launch checks use the resolved [admitted-major policy](java.md), including its declared preference and finite compatibility limits. Build and test the resulting pack separately before distributing it.
