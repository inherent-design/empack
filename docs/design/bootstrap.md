# Native engine bootstrap

Managed Prism and server distributions contain `.empack-tools/empack-bootstrap.jar` beside their launcher configuration or scripts, outside the game payload. This Java 8-compatible program selects an exact native empack engine and delegates an argument vector to it. Pack interpretation, acquisition, subscriptions, installation, runtime supervision and recovery remain in that engine. Standalone bundled snapshots and Modrinth exports do not require the bootstrap.

## Selection and compatibility

Generated commands request the exporter’s engine version. A distribution-local `empack` or `empack.exe` beside the JAR takes precedence when it reports that exact version. Otherwise the bootstrap uses its private user cache, then downloads the requested official release. It does not scan instances, follow a latest-version pointer, or upgrade a global installation. Preparation and launch request the same version independently of PATH or cache relocation.

Every delegated engine must report cancellation protocol `empack-bootstrap/1`; the first supporting engine is v0.8.5-beta. Display version and protocol capability are checked separately. The exact standalone `--bootstrap-protocol` invocation reports executable capability without loading user configuration, project files, or dotenv settings; it cannot be combined with an operation. A release descriptor's minimum engine requirement remains a separate compatibility check. A channel update cannot silently replace the engine selected by the launcher; rebuild and reimport the launcher distribution when intentionally changing that selection.

`--engine FILE` selects a strict local executable and fails on mismatch. `--development-engine` additionally permits an explicitly selected `0.0.0-dev` engine; it never admits that executable into a release cache slot. `--offline` prevents acquisition, while retaining matching distribution-local and cached engines. `--cache DIRECTORY` and `EMPACK_BOOTSTRAP_CACHE` select an isolated cache. The direct CLI passes arguments after `--` and inherits its working directory and streams. Generated entry points instead use the static invocation-file route below.

## Static invocation files

Managed exports place `prepare.json` and `launch.json` beside the JAR in `.empack-tools/`. Generated commands use ASCII relative paths and `-Dfile.encoding=UTF-8` before `-jar`, applied only to the bootstrap JVM. Prism runs from its game directory and uses `../.empack-tools/`; server scripts first select the distribution directory. The file reader resolves the distribution base above `.empack-tools` and starts native empack there. Relative engine arguments and an explicit relative `--engine` override resolve from that base, so moving the distribution does not retain an old absolute instance path.

The record has exactly four fields: `schema` is `empack-bootstrap-invocation/1`, `engine_version` is the exact native version, `arguments` is a nonempty array of literal strings, and `append_arguments` is a boolean. Preparation records bind the release digest, layout, side and enrollment requirement. Launch records carry the runtime/update flags and final `--`; only these records accept additional runtime arguments after the bootstrap command's own `--`. The CLI refuses a separate `--engine-version` alongside a file. For example, from a server distribution root:

```sh
java -Dfile.encoding=UTF-8 -jar .empack-tools/empack-bootstrap.jar --invocation-file .empack-tools/prepare.json
```

Admission captures one regular unlinked record under `.empack-tools`, bounds it to 1 MiB, permits at most 4,096 static arguments of 65,536 UTF-16 code units each, and requires strict UTF-8 and well-formed Unicode. Unknown/duplicate fields, unsupported schemas, incorrect types, NUL, truncation and trailing JSON are errors before engine selection. The captured input is checked for replacement while read and is not reopened for execution. Paths through tool-directory links or reparse points are refused. No shell evaluation, recursive file expansion or environment-variable interpolation occurs.

These static files remain part of the distribution, outside game ownership. They contain no dynamic game credentials; stdin and dynamically appended runtime arguments remain separate and are never written into them. File contents do not authorize another engine download source or bypass exact-version, cache or release verification. The cancellation connection carries lifetime signals only. See the [recipient encoding appendix](../troubleshooting.md#bootstrap-encoding-appendix) for external JVM limitations that cannot be recovered after launcher decoding.

## Official acquisition and cache

The fixed official GitHub release API supplies the exact tag, archive name, byte count and SHA-256 digest. Verified HTTPS authenticates that authority; the digest is not an independent publisher signature. Downloads use the fixed official repository and known target naming, ignoring executable URLs in response data. Redirects are limited to GitHub’s configured asset hosts, with no HTTP downgrade, credentials, cookies or certificate bypass. Unavailable releases, missing digests and rate limits fail without choosing another version.

Requests have a shared 180-second deadline, five redirects, a 4 MiB metadata limit and a 64 MiB compressed archive limit. Archive inspection bounds decoded bytes and entry counts; it rejects traversal, aliases, duplicate entries, links, special files, unsupported compression, checksum failures and wrong native targets before execution. Target selection follows the JVM process architecture for the five shipped native targets. Unsupported architectures and exposed musl environments are refused.

The cache lives under `empack/engines` in the platform's user cache directory. Exact version spelling is hashed for a case-sensitive key even on a case-insensitive filesystem. A target-specific writer lock covers acquisition and publication, with a bounded wait; it is released before delegated execution. Private candidates and their ownership journal precede writing. Verified engine objects are immutable, and an atomic ready record publishes their identity. Interrupted candidates can be reclaimed; an admitted backing that is missing, corrupt, linked or writable outside the accepted user boundary fails visibly. Local engines are never moved or changed. Cache lookup records content and permissions, without persisting inode identities across reboots. Refusals identify the affected cache record, backing or executable. Bootstrap-generated diagnostics escape line breaks and terminal controls in paths and other external text; native/game output remains delegated unchanged.

On POSIX filesystems, cache objects must match the home owner's identity and forbid group/other writes. New Windows cache directories receive an explicit inheritable home-based ACL atomically at creation, instead of inheriting a temporary parent's default ACL. Existing objects and competing creators' objects are validated without rewriting their permissions. On Windows, both object ownership and effective writable ACL entries must stay within the principals already allowed to write the user's home. Inherit-only entries describe descendants rather than access to the observed directory; each descendant is checked when used. The home and a new object need not name the same owner, for example when an administrative group owns the home. This does not admit another writer or change the home's permissions.

## Process lifetime

The JAR remains the native engine's parent. A nonce-authenticated loopback connection belongs to one invocation. Cancellation or loss of the Java parent feeds the existing native cancellation token. The native engine owns process retirement, terminal restoration and persisted runtime ownership; the bootstrap waits for its terminal result and preserves its exit status and diagnostics. It does not interpret a stopped process as retired or use Java `destroy()` as proof of runtime cleanup. The control descriptor is not passed to supervised game/tool processes.

Prism uses its selected `$INST_JAVA` for both preparation and wrapper execution. The wrapper leaves the original game Java program and JVM arguments in the delegated native argv; game flags are not applied to the bootstrap JVM. Server scripts use their existing `JAVA_HOME` or PATH Java selection. [Managed configuration validation](builds.md) and required server attributes apply to the resulting commands. Enrollment, signed-channel meaning, seed files, worlds and Prism icon ownership retain their ordinary engine checks.

## Build and qualification

The Java project remains in this repository. Its pinned modern JDK compiles with `--release 8`; packaged dependencies must retain that API and bytecode baseline. `python3 scripts/build-bootstrap.py` builds one shaded executable JAR and records its sources, version, hash and build tools. `--check` admits existing bytes without building or downloading. Cargo consumes this explicit input and refuses stale source or changed bytes; its build script does not build Java or use the network. Exporting with a packaged native empack therefore needs no JDK or bootstrap download.

CI builds the JAR once and tests those bytes across the admitted JVM majors. Native build evidence records the JAR identity emitted by Cargo. Release admission checks that all native archives embed the same JAR being published separately as `empack-bootstrap.jar`; nonpublishing candidate workflows retain their existing restrictions. Packaged-JAR fixtures, real terminal supervision and actual Prism import/preparation/wrapper checks establish different facts. A fixture pass does not establish a graphical launch or gameplay compatibility.
