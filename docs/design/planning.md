# Planning and authorization

A plan describes exact effects against a captured root and relevant read set.

| Phase | Input | Result |
| --- | --- | --- |
| Capture | Native root and required sources | Owned immutable observations, including absence |
| Normalize | Request, DTOs and catalog evidence | Validated semantic intent or exact release |
| Plan | Semantic state and observations | Changes, acquisitions, conflicts and expected postconditions |
| Decide | Revision-bound decision requests | Explicit alternatives and retained choice values |
| Authorize | Complete preview and host policy | Grant bound to plan identity and exact footprint |
| Execute | Grant and private candidate | Verified effects admitted to publication |

Capturing is distinct from effect-free planning. Preview may resolve providers and
use owned temporary scratch, but writes no project, journal, persistent cache,
subscription or tool installation. A declined or failed preparation leaves prior
managed state intact.

## Read sets

Capture content and control documents that affect the selected operation. Record
missing destinations and relevant ancestors. Unrelated oversized files or links
must not block a narrow removal unless they affect ownership or path safety.
Revalidate raw document revisions and native observations before publication.

Author operations use logical roots and required closure evidence. An instance
update uses the prior installation record and the selected complete release. Pack
identity, environment, choices and update authority are part of the plan binding.

Add, update, synchronization and adoption bind the union of prior and proposed
native placements. They do not discover another manager's records or maintain its
indexes. Files outside the selected footprint cannot confer ownership or invalidate
the operation merely by naming the same project or destination.

Provider adoption identifies installed bytes against the declared canonical project
and verifies every proposed placement before publishing intent and resolution.
Establishing the first lock requires explicit file placements or an exact provider
selection; an automatic placement without either is insufficient evidence. A
provider world keeps its exact archive selection and verifies its selected members.

Removal selects an exact logical key, an unambiguous title or a provider-qualified
identity such as `modrinth:AANobbMI`. An exact key takes precedence over title
matching. The selected native lock records determine placements and dependency
checks. Untracked files require adoption before managed removal; acknowledging
incomplete dependency evidence does not turn a filename into deletion authority.

## File planning

`plan_file` compares prior installed content, current native observation and incoming
release content. Its result contains a mutation, preservation decision or conflict.
The instance planner composes these decisions only after identity, destination,
collision and root checks. Unknown observation is not equivalent to absence.

Changed user bytes block ordinary replacement/deletion. A replacement decision must
be explicit and bound to those observed bytes. Seed preservation grants no future
authority over user files. See [instance reconciliation](instances.md).

## Batches

Author add/update defaults to `AllRequested`. Explicit `ContinueIndependent` joins
requests connected by shared identities, required dependencies, overlapping writes
or source-read relationships. A failed group retains its previous intent/content;
verified groups publish one coherent combined candidate with a nonzero partial
outcome. Unresolved identity cannot establish an independent footprint.

Release installation and activation are always all-requested for selected required
content. Optionality is decided before planning; failed optional acquisition is not
permission to silently change the selected choice.

## Postconditions and grants

A grant binds operation identity, plan revision, root, network origins, external
installer permission and replacement footprint. `--yes` supplies policy answers;
it does not bypass signature, ownership, collision or verification checks.

Postconditions include file inventory, permissions, exact documents and installed
release/choice state. Successful worker exit, a download count or a valid archive
header cannot substitute for those postconditions.
